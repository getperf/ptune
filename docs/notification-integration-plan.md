# OS標準通知の導入検討

2026-10-09時点の検討案。ptune本体への実装・採用完了を示す文書ではない。probeの帰結文書とDecision Cardは別途管理する。

## 確認した現状

- `lib/models/pomodoro_info.dart` の `PomodoroInfoDisplay.toDisplayString()` が `🍅x<planned> ✅x<actual>` を組み立てる。実績は小数1桁固定、nullなら実績部分を省略する。
- タスク一覧、タイマー画面、MyTaskの表示がこの処理を再利用する。全体集計はTaskStatsとsummary_viewによる別表示。
- 実績は経過時間をポモ単位へ換算したdouble。整数の完了セッション数に限定されない。
- TimerNotificationServiceはWORK完了時のスマホHapticFeedbackのみ。開始・OS通知・終了予約は未実装。
- 現在のハプティクス設定はStateProviderで、永続化していない。
- TimerControllerはタスク集計・更新を待った後に完了通知を呼ぶ。stop()は手動待機への内部遷移でも使われる。

## 表示案

タイトルは「🟢 作業開始」「🔴 作業終了」。手動停止を通知する場合は「🔴 作業停止」と区別する。本文は親の通知用名、子の作業名、既存のPomodoroInfo表示を各行に置く。

親がないタスクは親行を省略する。長文の通知用名は未決で、タスク永続化へ新フィールドを追加することは今回の前提にしない。タグ・🚫等の意味を推測して削除しない。

既存書式は `🍅x2 ✅x1.0`。小数末尾の0を落とす変更は通知だけで行わず、必要なら共通表示側の別判断とする。

## 設定画面案

- 開始通知 ON/OFF、終了通知 ON/OFF（初期値はともにOFFを推奨）。この2項目を全体ON/OFFより優先し、重複したスイッチを増やさない。
- OS通知の許可状態を別に表示し、「通知を許可」「OS通知設定を開く」「テスト通知」を用意する。
- Androidの終了予約に必要な特別アクセスは別状態で表示し、「予約時刻の設定」を用意する。
- アプリの希望設定とOSの許可状態を混同しない。設定画面復帰時にOS状態を再取得する。
- 終了通知をOFFにしたら未配信の予約を取り消す。ONにした時点で実行中なら残り時間で予約する。
- 現行の「バイブ通知」は「スマホ本体の振動」としてOS通知と区別する。通知音・振動はOS設定と時計設定に依存し、時計の強度を設定できるようには見せない。二重振動は実機確認する。
- 項目増加に合わせSettingsViewはスクロール可能にする。

| `lib/services/timer_notification_service.dart`（既存拡張） | タイマー通知方針、設定判定、文面・OS通知・既存ハプティクスの協調 |

## イベントと予約

| イベント | 推奨動作 |
|---|---|
| readyからWORK開始 | 開始通知を1回発行、終了時刻を予約 |
| 再開 | 終了予約を更新。開始通知の再発行は既定で行わない |
| 一時停止 | 終了予約を取消。停止通知は初期対象外 |
| 手動停止・リセット | 終了予約を取消。時間満了と混同しない |
| タスク切替 | 予約本文・対象タスクを更新。通知回数は増やさない |
| 時間満了 | 予約通知とアプリ内完了処理の二重通知を防ぐ |
| 自動遷移 | 次のWORK開始を明示的に扱う。内部stop()で停止通知を発行しない |

セッションIDと通知IDを対応させる。開始・完了の重複呼出し、取消と発行の競合、アプリ復帰時の照合を確認する。OS予約からアプリの集計や自動連続運転が保証されるわけではない。

## 終了通知の実績値に関する未決事項

OSに事前予約した本文は、予約時のスナップショットになる。終了時の確定実績が自動で反映されるとは限らない。現在の集計はタスク切替・中断を含むため「現在値+1」を確定実績として表示しない。

開始通知は現在の確定値を共通書式で表示する。終了予約は確定実績を省略するか「開始時」の値と明示する案を推奨し、終了後の確定実績表示を必須にする場合は別に設計する。通知だけのためにリモート保存完了を待たせない。

## probeからの引継ぎ

- 方針選択: ユーザーはOS標準通知で進め、②の色付き表示を分かりやすいと評価した。
- 確認済み: 添付の時計写真でテキスト通知表示と長文折り返しが確認できた。probeの前回解析・テスト2件・Android APKビルドは成功した。
- 未確認: 新しいポモ絵文字表示、小数入力、振動、ロック中予約・取消・再予約の測定、スマホ機種/OS・時計FW、iOSビルドと実機。
- probeは現在整数実績入力で、旧ポモ数書式。小数表示案はまだ実装済みとしない。
- 元の判断は通知方式と可読性。ptuneの製品受入、バックグラウンド時間整合、権限処理は後続の導入判断で扱う。

1. vaultの活動indexと既存Cardを確認し、probeの判断Card案を提示する。

4. ptune導入判断でイベント定義、終了予約本文の実績、設定・責務を確定してから実装する。
